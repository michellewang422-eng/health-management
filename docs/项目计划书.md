## 先读这里

**结论**：不要改 User-management-service，在它旁边新建 `health-service`（端口 8001），网页（端口 8777）同时调用两个后端。

我读了你仓库的代码，几个事实决定了整个方案：

- `users` 表只有 `id / email / first_name / last_name / created_at / updated_at`，没有年龄、性别、身高、体重。所以「用已做好的 User-management-service 管理用户资料」只能管**姓名和邮箱**；健康资料要另找地方存。
- 已有接口：`POST/GET/PUT/DELETE /users`、`GET /users?email=`、`POST /auth/login`（只输邮箱、无密码）。
- CORS 只放行了 `localhost/127.0.0.1` 的 `5500` 和 `8777` 端口，所以网页要从这两个端口之一打开。
- `requirements.txt` 里已经有 `httpx`，health-service 可以直接用它去调用 user-service（服务器调用服务器）。
- 你现有的测试风格是 `unittest` + `TestClient` + 内存 SQLite（`tests/_support.py`），新项目沿用同一套，不用学新工具。

**三天节奏**

- 第 1 天（后端基础，约 4.75 小时）：PR-01 到 PR-04。结束时，用 `/docs` 页面和 curl 就能完成「建档 → 改档 → 删档 → 看参考标准」。

   │  fetch                      │  fetch
   ▼                             ▼
user-service (8000)  ◀── httpx ── health-service (8001)
   │                                │

## 数据库怎么选

**结论**：用 SQLite。它和你的 user-service 一样，零安装、单文件、支持完整 SQL，完全够用一个人或几个人使用的健康记录。

| 数据库 | 类型 | 优点 | 缺点 | 什么时候选 |
| --- | --- | --- | --- | --- |
| SQLite | 关系型，单文件 | 零安装、备份=复制文件、支持 JOIN 和聚合 | 多人同时写入会排队，没有独立的用户权限 | 学习、原型、单机应用、低并发 |
| PostgreSQL | 关系型，独立服务器 | 并发强、类型丰富、权限完善 | 要安装和运维一个数据库服务 | 上线给很多人用、部署到云 |
| MySQL | 关系型，独立服务器 | 生态成熟、资料多 | 同上，且在复杂查询上通常不如 PostgreSQL 灵活 | 团队已经在用 MySQL |
| MongoDB | 文档型 | 结构自由，适合形状不固定的数据 | 做「每天一行，按日期汇总」这类统计不如 SQL 自然 | 日志、形状多变的内容 |

**四个判断问题**，以后选库都可以用：

1. 数据结构固定吗？本项目：固定（每天一行，字段一样）→ 关系型。
2. 需要 JOIN 或汇总吗？本项目：需要（周期报告要按日期求平均、对比标准）→ SQL 更自然。
3. 同时写入的人多吗？本项目：几乎没有 → SQLite 够用。
4. 部署在哪里？本项目：本机 → 文件式数据库最省事。

**升级路径**：以后换 PostgreSQL，因为用了 SQLAlchemy，主要改 `DATABASE_URL` 这一行，并删掉 SQLite 专属的 `connect_args={"check_same_thread": False}`。

## 测试怎么写

沿用你 user-service 的写法：`unittest` + `TestClient` + 内存 SQLite，共用一个 `tests/_support.py`。每个用例分三段：准备（Arrange）、执行（Act）、断言（Assert）。

```python
class ProfileAPITestCase(DBTestCase):
    def test_create_profile_returns_201(self):
        # Arrange：造输入
        payload = {"user_id": 1, "age": 35, "gender": "female",
                   "height_cm": 165, "weight_kg": 60}
        # Act：调用被测的东西
        resp = self.client.post("/profiles", json=payload)
        # Assert：检查结果
        self.assertEqual(resp.status_code, 201)
        self.assertEqual(resp.json()["weight_kg"], 60)
```

**本项目的 6 条测试约定**

1. 每个 PR 至少四类用例：正常路径、边界值（刚好等于上下限）、错误输入、回归（以前对的东西没坏）。
2. 命名用 `test_<场景>_<预期>`，如 `test_age_17_is_rejected`，失败时不用打开代码就知道哪里坏了。
3. **预期值先用计算器或手算，再写进测试**。不要先跑代码拿输出当预期，那样代码错了测试也会跟着错。
4. 纯计算函数（BMR、打分）直接调用测试，不走 HTTP、不碰数据库，速度最快。
5. 跨服务（以及选做的 AI）都用「替身」：用 `app.dependency_overrides` 把真实的 user-service 客户端（AI 客户端同理）换成假的，测试不依赖网络和密钥。
6. 前端用「手动验证清单」（每个 PR 里写清步骤和预期），不引入前端测试框架。

运行：`python -m unittest discover -v`。只跑一个文件：`python -m unittest tests.test_profiles -v`。

## PR-01 脚手架和第一个 server（0.5 h）

**目标**：新建仓库 `health-management`，让 `health-service` 在 8001 端口跑起来，有 `GET /health`，并写出第一个测试。

**需要的知识**

- server = 一个持续运行、监听某个端口、收到 HTTP 请求就返回响应的程序；一个端口同一时刻只能被一个程序占用。
- HTTP 请求由「方法 + 路径 + 请求头 + 请求体」组成，响应由「状态码 + 响应头 + 响应体」组成。

## PR-02 数据库和 health\_profiles 表（1 h）

**目标**：连上 SQLite，用 Python 建出 `health_profiles` 表，并用 `sqlite3` 命令行自己写几条 SQL。

**需要的知识**

- 关系型数据库的基本概念：表、行、列、主键（每行的身份证）、`UNIQUE`（不能重复）、`NOT NULL`、索引（让查找更快）。

## PR-03 Profile CRUD 并对接 user-service（2 h）

**目标**：做出健康档案的增查改删接口；建档前先调用 user-service 确认用户存在；必填项、数值范围、默认 30 天周期都在这一步实现。这是第 1 天最难的一个 PR。

**需要的知识**

- **API 是什么**：一套「用方法 + 地址表达意图」的约定。增 `POST`、查 `GET`、改 `PUT`、删 `DELETE`；状态码告诉客户端结果（201 已创建、204 成功且无内容、404 找不到、409 冲突、422 数据不合法、502 上游服务出错）。
- Pydantic 校验：`Field(ge=, le=)` 限制范围，`Literal[...]` 限制只能从几个值里选，`model_validator` 校验多个字段之间的关系。
- 依赖注入 `Depends`：把「查 user-service」包成一个可替换的依赖，测试时换成假的。
- **服务器调用服务器**：用 `httpx` 在 Python 里发 HTTP 请求，必须设超时，并把对方挂了翻译成自己的 502。
- 为什么建档前要查 user-service：没有数据库外键帮你卡住，就得由代码自己保证「不会出现没有主人的健康档案」。

**怎么做**

1. `app/schemas.py`：三个模型——`ProfileIn`（可编辑的字段）、`ProfileCreate`（加 `user_id`）、`ProfileOut`（加 `id` 和时间戳）。必填项不给默认值，选填项默认 `None`：

```python
from datetime import date, datetime
from typing import Literal, Optional
from pydantic import BaseModel, ConfigDict, Field, model_validator


class ProfileIn(BaseModel):
    # ---- 必填 ----
    age: int = Field(ge=18, le=100)
    gender: Literal["male", "female"]
    height_cm: float = Field(ge=100, le=250)
    weight_kg: float = Field(ge=30, le=300)
    # ---- 选填 ----
    baseline_glucose_mgdl: Optional[float] = Field(default=None, ge=40, le=600)
    baseline_cholesterol_mgdl: Optional[float] = Field(default=None, ge=80, le=500)
    baseline_systolic: Optional[int] = Field(default=None, ge=70, le=250)
    baseline_diastolic: Optional[int] = Field(default=None, ge=40, le=150)
    goal_type: Literal["lose_weight", "maintain", "gain_weight"] = "maintain"
    goal_note: Optional[str] = Field(default=None, max_length=200)
    cycle_days: int = Field(default=30, ge=7, le=365)   # 没填就是 30 天
    start_date: Optional[date] = None                   # 没填就是建档当天

    @model_validator(mode="after")
    def check_blood_pressure(self):
        s, d = self.baseline_systolic, self.baseline_diastolic
        if (s is None) != (d is None):
            raise ValueError("血压必须同时提供收缩压和舒张压")
        if s is not None and s <= d:
            raise ValueError("收缩压必须大于舒张压")
        return self


class ProfileCreate(ProfileIn):
    user_id: int = Field(ge=1)


class ProfileOut(ProfileCreate):
    id: int
    start_date: date          # 返回时一定有值（覆盖掉父类的 Optional）
    created_at: datetime
    updated_at: datetime

    model_config = ConfigDict(from_attributes=True)   # 允许直接用数据库对象构造
```

USER_SERVICE_URL = "http://127.0.0.1:8000"

        return True
    if r.status_code == 404:
        return False
    raise UserServiceUnavailable()   # 500 等其它情况


def get_user_checker():
    """依赖函数：路由通过 Depends(get_user_checker) 拿到 user_exists，测试时可整个换掉。"""
    return user_exists

3. `app/routers/profiles.py`：五个接口。建档和更新的核心写法：

```python
router = APIRouter(prefix="/profiles", tags=["profiles"])


def get_profile_or_404(db: Session, user_id: int) -> HealthProfile:
    profile = db.query(HealthProfile).filter(HealthProfile.user_id == user_id).first()
    if not profile:
        raise HTTPException(status_code=404, detail="健康档案不存在")
    return profile


@router.post("", response_model=ProfileOut, status_code=201)
def create_profile(payload: ProfileCreate,
                   db: Session = Depends(get_db),
                   user_exists=Depends(get_user_checker)):
    try:
        found = user_exists(payload.user_id)
    except UserServiceUnavailable:
        raise HTTPException(status_code=502, detail="用户服务暂时不可用")
    if not found:
        raise HTTPException(status_code=404, detail="用户不存在，请先注册")
    if db.query(HealthProfile).filter(HealthProfile.user_id == payload.user_id).first():
        raise HTTPException(status_code=409, detail="该用户已建过健康档案")
    # exclude_none：start_date 没传时让模型的默认值（今天）生效
    profile = HealthProfile(**payload.model_dump(exclude_none=True))
    db.add(profile)
    db.commit()
    db.refresh(profile)
    return profile


@router.put("/{user_id}", response_model=ProfileOut)
def update_profile(user_id: int, payload: ProfileIn, db: Session = Depends(get_db)):
    profile = get_profile_or_404(db, user_id)
    for key, value in payload.model_dump().items():
        if key == "start_date" and value is None:
            continue                 # 没传开始日期 = 保持原来的
        setattr(profile, key, value)  # 选填项传 None = 清空
    db.commit()
    db.refresh(profile)
    return profile
```

`GET` 用 `get_profile_or_404`；`DELETE` 删除后返回 204（PR-05 建好 `daily_logs` 后，回来加一句「同时删掉该用户的所有每日记录」）。在 `main.py` 里 `include_router`。

## PR-04 参考标准引擎（1.25 h）

**目标**：根据年龄、性别、身高、体重、目标，算出每日热量、运动时长与项目、健康体重范围、血糖血压血脂参考值，并对用户填写的原始指标给出评估。

**需要的知识**

- **纯函数**：同样的输入永远得到同样的输出，不读数据库、不联网。所有计算写成纯函数，就能不启动 server 直接测试。
- 公式：BMI、Mifflin-St Jeor 基础代谢（BMR）、每日总消耗（TDEE = BMR × 活动系数）。
- 「常量表 + 分类函数」的写法：阈值写在一个地方，改标准不用改逻辑。
- 边界值的写法：`<` 还是 `<=` 会决定 100 mg/dL 算正常还是偏高，每一个边界都要有测试。

**诚实说明一件事**：成人指南里的空腹血糖、血压、总胆固醇分类标准**不按年龄和性别分组**；真正随年龄性别变的是热量、运动建议、健康体重范围和 HDL（好胆固醇，男 ≥ 40、女 ≥ 50 mg/dL）。网页上要把这点说清楚，不要假装血糖标准对 25 岁和 65 岁不同。

**规则总表**（写进 `app/services/standards.py` 的常量）

| 项目 | 规则 |
| --- | --- |
| BMI | 体重 kg ÷ 身高 m²，保留 1 位小数；< 18.5 偏瘦，18.5–24.9 正常，25–29.9 超重，≥ 30 肥胖 |
| 健康体重范围 | BMI 18.5 到 24.9 对应的体重 |
| BMR | 男：10×体重 + 6.25×身高 − 5×年龄 + 5；女：同上最后改为 − 161 |
| 每日热量 | BMR × 1.375；减重 − 500，增重 + 300；不低于女 1200 / 男 1500；最后四舍五入到 10 的倍数（避免假精确；用「加 0.5 再向下取整」，不用 Python 的 `round()`，因为它遇到 .5 会取偶数） |
| 目标体重变化 | 减重 − 0.5 kg/周；增重 + 0.25 kg/周；维持 0 |
| 每日运动 | 维持 / 增重 30 分钟；减重 45 分钟（折算成「中等强度分钟」） |
| 强度折算 | 低强度 × 0.5，中等 × 1，高强度 × 2（即 1 分钟高强度 = 2 分钟中等强度） |
| 推荐项目 | 18–39 岁：快走、慢跑、骑行、游泳 + 力量训练 2 天/周；40–64 岁：快走、游泳、骑行 + 力量训练 2 天/周；65 岁及以上：散步、太极、平衡训练 + 轻量力量训练 |

import math

ACTIVITY_FACTOR = 1.375


def calc_bmi(weight_kg, height_cm):
    m = height_cm / 100
    return round(weight_kg / (m * m), 1)


def calc_bmr(gender, age, height_cm, weight_kg):
    base = 10 * weight_kg + 6.25 * height_cm - 5 * age
    return base + 5 if gender == "male" else base - 161


def daily_calories(gender, age, height_cm, weight_kg, goal_type):
    tdee = calc_bmr(gender, age, height_cm, weight_kg) * ACTIVITY_FACTOR
    adjust = {"lose_weight": -500, "maintain": 0, "gain_weight": 300}[goal_type]
    floor = 1500 if gender == "male" else 1200
    target = max(tdee + adjust, floor)
    # 不用 round()：它遇到 .5 会「取偶数」（如 round(2.5) == 2），和「四舍五入」不一致
    return int(math.floor(target / 10 + 0.5)) * 10

## PR-05 每日记录和打分（2 h）

**目标**：用户每天输入体重、运动时间、运动强度、摄入热量；系统拿实际值和 PR-04 的标准对比，给每一项打「超额 / 完成 / 未完成」，并把结果放进追踪表（接口返回的列表）。

**需要的知识**

- 建第 2 张表 `daily_logs`，用**联合唯一约束** `UNIQUE(user_id, log_date)`：一人一天只能有一行。
- **upsert**：同一天提交两次应该是覆盖而不是报错也不是两行。
- 多源数据计算：打分需要「档案 + 标准 + 当天记录」三样东西。
- SQL 查询：`WHERE`、`ORDER BY`、`BETWEEN`；以及下一个 PR 会用到的 `COUNT / AVG / SUM`。
- **浮点数边界**：`1780 * 1.1` 等于 `1958.0000000000002`。比较前对比值先 `round(ratio, 4)`，否则刚好等于阈值的数据会被判错。

**打分规则**（写进 `app/services/scoring.py`，纯函数）

| 指标 | 超额 `exceeded` | 完成 `met` | 未完成 `missed` |
| --- | --- | --- | --- |
| 运动（折算分钟 ÷ 目标） | ≥ 120% | 90%–<120% | < 90% |
| 热量（摄入 ÷ 目标） | > 110%（摄入超标） | 90%–110% | < 90%（摄入不足） |
| 体重（实际 − 当天期望体重）减重 | ≤ −0.5 kg | −0.5 kg < 差 ≤ +0.3 kg | > +0.3 kg |
| 体重 增重 | ≥ +0.5 kg | −0.3 kg ≤ 差 < +0.5 kg | < −0.3 kg |
| 体重 维持 | — | 差的绝对值 ≤ 1.0 kg | 其它 |

- 当天期望体重 = 起始体重 + 每周变化 × （log\_date − start\_date）天数 ÷ 7。
- 「超额」对不同指标意义不同，所以每项还带一个 `tone`：`good`（好）、`warn`（提醒）、`bad`（没做到）。规则：`met` 一律 `good`；`missed` 一律 `bad`；`exceeded` 默认 `good`，唯独**热量超标且目标不是增重时是 `warn`**。
- 当天得分 = `good` 的项数；没填的指标不计入分母（例如只填了运动和热量，就是「x/2」）。
- 打分结果**不存库**，每次读取时用最新档案重算。

**怎么做**

1. `app/models.py` 加 `DailyLog`（列见「数据模型」表 2），表参数里写 `UniqueConstraint("user_id", "log_date")`；因为 `create_all` **不会修改已存在的表**，而新表会被自动建出来，所以这一步不用删库。
2. `schemas.py` 加 `LogIn`（`weight_kg` 选填 30–300；`exercise_minutes` 0–600 默认 0；`exercise_intensity` 默认 `moderate`；`exercise_type` 选填 ≤ 50 字；`calories_in` 选填 0–10000）和 `LogOut`。
3. `scoring.py` 的打分函数（运动、热量如下；体重打分见下面的 `score_weight`，睡眠在 PR-08.5 加 `score_sleep`）：

```python
EXERCISE_EXCEED, EXERCISE_MET = 1.2, 0.9
CAL_HIGH, CAL_LOW = 1.1, 0.9


def score_exercise(effective_min, target_min):
    ratio = round(effective_min / target_min, 4)
    if ratio >= EXERCISE_EXCEED: return "exceeded"
    if ratio >= EXERCISE_MET:    return "met"
    return "missed"


def score_calories(calories_in, target):
    ratio = round(calories_in / target, 4)
    if ratio > CAL_HIGH: return "exceeded"
    if ratio >= CAL_LOW: return "met"
    return "missed"


def expected_weight(start_weight, goal_type, start_date, log_date):
    # 周期开始之前的日期按 0 天算，期望体重 = 起始体重
    days = max((log_date - start_date).days, 0)
    return start_weight + weekly_weight_change(goal_type) * days / 7


WEIGHT_LOSE_EXCEED, WEIGHT_LOSE_MET = -0.5, 0.3
WEIGHT_GAIN_EXCEED, WEIGHT_GAIN_MET = 0.5, -0.3
WEIGHT_MAINTAIN_TOLERANCE = 1.0


def score_weight(actual, expected, goal_type):
    diff = round(actual - expected, 4)          # 先 round，避免 0.3000000000000682 这类浮点误差
    if goal_type == "lose_weight":
        if diff <= WEIGHT_LOSE_EXCEED: return "exceeded"
        if diff <= WEIGHT_LOSE_MET:    return "met"
        return "missed"
    if goal_type == "gain_weight":
        if diff >= WEIGHT_GAIN_EXCEED: return "exceeded"
        if diff >= WEIGHT_GAIN_MET:    return "met"
        return "missed"
    return "met" if abs(diff) <= WEIGHT_MAINTAIN_TOLERANCE else "missed"
```

## PR-06 前端骨架和登录（0.75 h）

**目标**：做出网页的外壳（导航栏、样式、统一的请求工具）和登录页；用户登录后能在每一页看到自己的名字。这是你第一次从 client 端去调用 server。

**需要的知识**

- **Client 端** = 浏览器里跑的 HTML + CSS + JavaScript。HTML 写内容结构，CSS 写样子，JavaScript 写行为并负责和 server 说话。
- `fetch` + `async/await` + JSON：发请求、等响应、把文字解析成对象。
- DOM：用 JS 改网页内容（`document.querySelector`、`textContent`、`addEventListener`）。
- **同源策略和 CORS**：浏览器默认不允许 8777 端口的网页去读 8000 端口的响应，除非 server 在响应头里明确允许。PR-01 里的 `CORSMiddleware` 就是在做这件事。
- `localStorage`：浏览器里按网站保存的小字典，刷新不丢。
- 静态文件也需要一个 server 来提供：`python3 serve.py 8777`（`health-web/serve.py`，和 `python3 -m http.server` 一样，但响应头带 `Cache-Control: no-store`，改了页面刷新就生效，不会读到旧的缓存）。

  if (!data || !data.detail) return `请求失败 (${status})`;

  return data.detail.map(e => `${e.loc.slice(1).join(".")}: ${e.msg}`).join("；");

async function request(base, path, options = {}) {
  let resp;

    resp = await fetch(base + path, {

      ...options,
    });
  } catch (e) {
    throw new Error("无法连接服务器，请确认后端已启动");   // 网络层错误
  }
  if (resp.status === 204) return null;
  const data = await resp.json().catch(() => null);
  if (!resp.ok) throw new Error(errorText(data, resp.status));
  return data;
}

## PR-08.5 睡眠时长：档案、打卡、打分（0.75 h）

**目标**：注册时多问一题「平时每晚睡几小时」，每日打卡里多记一项「昨晚睡了几小时」，按睡眠标准打「偏短 / 完成 / 偏长」，并显示在参考标准卡片和追踪表里。PR-09 的报告和曲线图再接着加睡眠。

**为什么单独成一个 PR**：PR-01 到 PR-08 已经合并，睡眠要回头改 PR-02（表）、PR-03（校验）、PR-04（标准）、PR-05（打分）、PR-07 和 PR-08（页面）五六处。把它集中在一个 PR 里，一次改完、一次测完，比散落到每个旧 PR 里清楚。

**需要的知识**

- **给已有表加列**：`create_all` 只建新表，不改旧表，所以开发期直接删掉 `health.db` 重启（和「风险与对策」里的做法一致）。以后有真实数据要用 `ALTER TABLE ... ADD COLUMN`，且给「必填」新列加到旧表时必须有默认值。
- **一个字段沿着数据流走一遍**：模型 → schema 校验 → 标准 → 打分 → 路由 → 页面。以后加任何新指标都是这条路线，这个 PR 是一次完整练习。
- **区间型标准**：睡眠不是「越多越好」，也不是「接近目标值」，而是落在一个区间里算达标。它的打分写法和 PR-05 的「实际 ÷ 目标」不同。
- 为什么没填睡眠的旧记录不会被扣分：没填的指标不计入分母（PR-05 已有的规则），所以老数据的 3/3、2/3、1/3 不变。

**规则总表**（写进 `standards.py` 和 `scoring.py`）

| 项目 | 规则 |
| --- | --- |
| 档案字段 | `sleep_hours`：选填，2–14 小时，页面步长 0.5；含义是「平时每晚平均睡眠」 |
| 每日记录字段 | `sleep_hours`：选填，0–24 小时，页面步长 0.25；记在**醒来那天**（周三早上醒来，睡了 7.5 小时，就记在周三） |
| 参考睡眠 | 18–64 岁：7–9 小时；65 岁及以上：7–8 小时（页面上显示的建议区间）。这一项会随年龄变（和血糖血压不同）。依据：AASM/SRS 2015 共识——成人规律睡眠应 ≥ 7 小时，长期 < 7 小时与多种健康风险相关；NSF 2015——18–64 岁 7–9 小时、65 岁及以上 7–8 小时 |
| 打分 | 小时 < 下限（7）→ `missed`；下限 ≤ 小时 ≤ 上限 → `met`；高于上限 → `exceeded`。比较前先 `round(hours, 2)`，所以 6.99 小时按 6.99 算偏短，7.0 小时算完成 |
| 页面小字 | 睡眠参考值旁固定显示一行小字写明依据并带链接（见下面第 5 步）；文字和链接由后端 `standards.sleep.sources` 提供，页面只负责显示 |
| `tone` | `met` → `good`；`missed` → `bad`；`exceeded` 一律 `warn`（睡太多不是「超额完成」，是提醒） |
| 当天得分 | `good` 的项数；没填睡眠不计入分母，所以满分从 x/3 变成最多 x/4 |
| 基线评估 | 档案里的平时睡眠与区间比较：`short` / `normal` / `long`，放进 `baseline_assessment.sleep`；档案没填睡眠时是 `null` |
| 徽章文字 | 睡眠专用：`missed` 显示「偏短」，`met` 显示「完成」，`exceeded` 显示「偏长」（不能直接用「超额」） |

**怎么做**

1. **模型**：删掉 `health.db`。`HealthProfile` 加 `sleep_hours = Column(Float)`（选填）；`DailyLog` 加 `sleep_hours = Column(Float)`（不写 `nullable=False` = 选填）。
2. **校验**：`ProfileIn` 加 `sleep_hours: Optional[float] = Field(default=None, ge=2, le=14)`（默认 `None` = 选填）；`LogIn` 加 `sleep_hours: Optional[float] = Field(default=None, ge=0, le=24)`；`LogOut` 同步。
3. **标准**（`standards.py`，纯函数）：

```python
def sleep_range(age):
    """参考睡眠区间（小时）。成人 7–9；65 岁及以上 7–8。依据见 SLEEP_SOURCES。"""
    return (7.0, 8.0) if age >= 65 else (7.0, 9.0)


def classify_sleep(hours, age):
    if hours is None:          # 档案没填睡眠
        return None
    lo, hi = sleep_range(age)
    h = round(hours, 2)
    if h < lo:
        return "short"
    return "normal" if h <= hi else "long"
```

   `build_standards` 返回里加 `"sleep": {"min_hours": 7, "max_hours": 9, "sources": SLEEP_SOURCES}`；`SLEEP_SOURCES` 是写在 `standards.py` 里的常量（文字和链接只写这一处）：

```python
SLEEP_SOURCES = [
    {"name": "AASM/SRS 2015 共识：成人每晚应睡 7 小时或以上，长期少于 7 小时与多种健康风险相关",
     "url": "https://pmc.ncbi.nlm.nih.gov/articles/PMC4434546/"},
    {"name": "NSF 2015 睡眠时长建议：18–64 岁 7–9 小时，65 岁及以上 7–8 小时",
     "url": "https://pubmed.ncbi.nlm.nih.gov/29073412/"},
]
```

   `baseline_assessment` 加 `"sleep": classify_sleep(profile.sleep_hours, profile.age)`。

4. **打分**（`scoring.py`）：

```python
def score_sleep(hours, age):
    lo, hi = sleep_range(age)
    h = round(hours, 2)
    if h < lo:  return "missed"
    if h <= hi: return "met"
    return "exceeded"
```

## PR-09 周期报告和曲线图（1.5 h）

**目标**：监测周期结束时（也支持周期中途预览），把追踪表里的数值画成曲线图：体重实际 vs 目标、运动实际 vs 目标、热量实际 vs 目标、睡眠实际 vs 达标区间，并给出汇总数字（你的第 4 条需求）。睡眠相关字段来自 PR-08.5。

**需要的知识**

- SQL 聚合：`COUNT / AVG / SUM`，在 SQLAlchemy 里是 `func.count()`、`func.avg()`、`func.sum()`。
- 「过滤后的日期区间」：只统计 `start_date` 到 `start_date + cycle_days − 1` 之间的记录。
- 为什么报告里要填满没打卡的日子：曲线图的横轴要完整的 30 天，没打卡的天数值为 `null`（图里显示为断点或连线）。
- 除法分母为 0：没有任何打卡时「完成率」是 `null`，不是 0，也不能报错。
- Chart.js：用 `<canvas>` + 一个配置对象画图；`labels` 是横轴，`datasets` 是每条线。从 CDN 引入时固定主版本（`chart.js@4`）。

**报告接口结构**（`GET /profiles/{user_id}/report`）

```json
{
  "cycle": {"start_date": "2026-10-01", "end_date": "2026-10-30", "days": 30, "elapsed_days": 3, "is_finished": false},
  "series": [
    {"date": "2026-10-01", "weight_kg": 60.0, "target_weight_kg": 60.0,
     "exercise_effective_min": 50, "target_exercise_min": 45,
     "calories_in": 1300, "target_calories": 1280,
     "sleep_hours": 5.5, "target_sleep_min_hours": 7, "target_sleep_max_hours": 9}
  ],
  "summary": {
    "logged_days": 3, "points": 7, "scored": 12, "completion_rate_pct": 58.3,
    "avg_calories": 1300, "total_exercise_minutes": 130, "weight_change_kg": -0.8,
    "avg_sleep_hours": 7.5,
    "status_counts": {
      "weight":   {"exceeded": 1, "met": 2, "missed": 0},
      "exercise": {"exceeded": 1, "met": 1, "missed": 1},
      "calories": {"exceeded": 1, "met": 1, "missed": 1},
      "sleep":    {"exceeded": 1, "met": 1, "missed": 1}
    }
  }
}
```

`series` 每天一项，共 `cycle_days` 项；没打卡的天其余字段为 `null`（目标字段仍然有值，图上目标线要连贯；睡眠的两条目标线是建议下限 7 和上限 9，65 岁及以上是 7 和 8）。`is_finished` = 今天 > `end_date`。`status_counts.sleep` 里 `exceeded` 的含义是「睡得偏长」，`missed` 是「睡得偏短」。上面的示例用的是 PR-08.5 验证表里带睡眠的 3 天数据。

**怎么做**

1. `report.py`（或 `routers/report.py`）：先 `filter(user_id, log_date.between(start, end))` 取出周期内所有记录转成字典 `{date: log}`，再用 `for i in range(cycle_days)` 生成每一天的 `series`。
2. 汇总这一步用 SQL 聚合替代 Python 循环来算平均热量、运动总分钟：

```python
from sqlalchemy import func

row = (db.query(func.count(DailyLog.id),
                func.avg(DailyLog.calories_in),
                func.sum(DailyLog.exercise_minutes),
                func.avg(DailyLog.sleep_hours))
         .filter(DailyLog.user_id == user_id,
                 DailyLog.log_date.between(start, end))
         .one())
logged_days, avg_calories, total_minutes, avg_sleep = row   # avg_sleep 保留 1 位小数；没有睡眠记录时是 None
```

对应的原始 SQL：`SELECT COUNT(id), AVG(calories_in), SUM(exercise_minutes), AVG(sleep_hours) FROM daily_logs WHERE user_id = 1 AND log_date BETWEEN '2026-10-01' AND '2026-10-30';`。`AVG` 会自动跳过 `NULL`，所以只填了几天睡眠就只按那几天平均。体重变化用「周期内最后一个有体重的记录 − 第一个有体重的记录」，不足两个体重时为 `null`。

3. 用 PR-05 的 `build_log_out`（PR-08.5 之后已经带睡眠）给每条记录打分后统计 `status_counts`（四项：weight / exercise / calories / sleep）、`points`、`scored`；`completion_rate_pct = round(points / scored * 100, 1)`，`scored == 0` 时为 `null`。

5. 前端 `report.html`：顶部显示状态条（「周期已结束」或「进行中，第 12/30 天，当前为预览」）、汇总卡片（含平均睡眠），以及四张图，体重图写法如下：

## PR-10 卡路里计算器（1.25 h）

**目标**：用户输入当天吃的食物名称和大概重量（克），系统算出总摄入热量，并可一键填入今天的打卡（你的第 5 条需求）。

**需要的知识**

- 第 3 张表 `food_items`：为什么食物热量要放在数据库里（可查、可加、可改）而不是写死在代码里。
- **种子数据（seed）**：程序第一次启动时把常见食物填进表里；必须是「幂等」的——跑两次结果和跑一次一样。
- SQL `LIKE '%关键字%'` 做模糊查询；用 ORM 时参数会自动绑定，不会被 SQL 注入。
- 请求体里的数组：`items: [{name, grams}, ...]`，用 Pydantic 的 `list[...]` 校验，`min_length=1`。
- 前端：动态增减行、**自绘的候选下拉**（不用 `<datalist>`：它不显示「别名命中」的候选，比如输入「鸡肉」时看不到鸡胸肉、鸡腿肉）、防抖（输入停下 300 ms 后再发查询）。
- **别替用户做决定**：「鸡肉」可能是鸡胸也可能是鸡腿，热量不同；候选不止一个时让用户自己选，不默认选第一个或名字最短的。

**计算规则**

- 匹配分四层，只取第一个有结果的层（英文不区分大小写）：① 名字完全一致（含去掉括号的名字，「米饭」命中「米饭（熟）」）→ ② 别名完全一致 → ③ 名字或别名包含关键字 → ④ 关键字里包含某个食物名或别名（如「烤鸡胸肉」含「鸡胸」，取最长的词，至少 2 个字，单字「蛋」不算，避免「蛋糕」误配）。
- **候选个数决定结果**：0 个 → 没找到（`unmatched`）；恰好 1 个 → 确定，计入总数；多于 1 个 → 有歧义（`ambiguous`），不计入总数，列出最多 8 个选项让用户选。
- 每项热量 = 克数 ÷ 100 × 每 100 g 千卡，保留 1 位小数；总热量 = 各项相加，保留 1 位小数；没匹配到的食物不计入总数，单独列在 `unmatched` 里；有歧义的食物也不计入总数，列在 `ambiguous` 里。
- 克数必须 > 0 且 ≤ 5000。

**怎么做**

1. `models.py` 加 `FoodItem`（列见「数据模型」表 3）；`seed_foods.py` 里写 `seed(db)`：对每种食物先查 `name` 是否存在，不存在才插入；已存在且 `source == "seed"` 的，如果别名变了就同步更新别名（这样改了别名表，旧数据库不用删库也生效，AI 估算的不碰）。在 `main.py` 的 `lifespan`（服务启动时执行一次）里调用，不要放在 import 时，否则测试一 import 就会去改开发用的 `health.db`。

```python
def item_kcal(grams: float, kcal_per_100g: float) -> float:

```

**实际实现补充（第一次对着真实服务运行之后）**

- 冒烟测试第一次真实运行在第 1 步就失败了：User-management-service 创建用户返回 **200**，脚本断言的是 201。单元测试用的是替身，发现不了这种「接线」差异，这正是端到端测试存在的理由。现在断言同时接受 200 / 201。

  - 答：如果断言先失败，`uid` 还没赋值，`finally` 就会因为 `uid is None` 跳过清理，留下测试用户。先记下 id 再断言，任何一步失败都能清理干净。

## 选做扩展 E-1：用 AI 让计算器更好用、更准（约 1.25 h）

**这一节是选做。** 主线 PR-01 到 PR-11 做完、所有测试通过之后再做。它只在现有接口旁边新增三个接口和一个页面输入框，**不修改任何主线代码的行为**：没有 key、没有网络、或者干脆不做这一节，网站的五项功能都照常使用。

**开始前确认**：`python -m unittest discover -v` 全绿；`scripts/smoke_test.py` 通过。做完后这两项必须仍然通过。

**本节新增的接口**（主线 API 总表里没有它们）

| 方法 + 路径 | 作用 | 成功 | 常见失败 |
| --- | --- | --- | --- |
| `POST /foods/estimate` | 估算未知食物的每 100 g 热量并存入 `food_items`（`source = "ai"`） | 200 | 502；503 |
| `POST /ai/report-summary` | 用人话解释周期报告 | 200 | 503 |

**密钥规则**：`ANTHROPIC_API_KEY` 只放 health-service 的环境变量，不进前端、不进 git。这是理解「为什么需要后端」的最好例子。

**对应的学习点**：怎么让 AI 变得可靠。完成后能回答：哪些事交给 AI（理解自然语言、估算），哪些事必须交给代码（所有数字计算和校验）。


**目标**：用 Claude API 解决三件人工做很繁琐的事，同时保证**数字仍然由 Python 算**，AI 出错不会污染数据。

| 功能 | AI 做什么 | Python 做什么 | 优先级 |
| --- | --- | --- | --- |
| A. 一句话记一餐 | 把「一碗米饭加两个水煮蛋」拆成「米饭 150 g、鸡蛋 100 g」这样的结构化列表 | 用 PR-10 的计算器算热量 | 必做 |
| B. 未知食物估算 | 对数据库没有的食物给出每 100 g 千卡 | 检查范围 0–900，通过后存入 `food_items`（`source='ai'`） | 应做 |
| C. 周期总结 | 把 PR-09 的汇总数字用人话写成 3 条建议 | 所有数字来自报告接口，不让 AI 自己算 | 有时间再做 |

**需要的知识**

- LLM API 的调用方式：发送 `messages`，设置 `system` 提示词，收到响应；按字数计费，所以要限制输入长度。
- **结构化输出（tool use）**：给模型一个工具的 JSON Schema，并强制它调用这个工具，这样拿到的是有固定字段的 JSON，不用从文字里猜。
- **不要盲信 AI 的输出**：用 Pydantic 再校验一遍（克数 > 0 且 ≤ 2000、食物名长度、项目数 ≤ 15），不合格就拒绝。
- API key 是密码：只放在 health-service 的环境变量 `ANTHROPIC_API_KEY`（可写在不进 git 的 `.env`），绝不出现在网页代码里——这就是「为什么需要 backend」的答案。
- 优雅降级：没有 key 或网络不通时，AI 接口返回 503，普通计算器照常可用。
- 提示词注入：用户输入的文字可能写着「忽略以上指令」，所以 AI 的输出只能当数据，必须过校验。

**怎么做**

1. `pip install anthropic`（再 `pip freeze > requirements.txt`），把 key 写进 `.env`（`.gitignore` 已忽略），启动 server 前 `export ANTHROPIC_API_KEY=...`。模型名用环境变量配置：解析餐食用快且便宜的 `claude-haiku-4-5-20251001`，写总结可以用 `claude-sonnet-5-5`。
2. `app/services/ai_client.py`（把 AI 调用包成一个类，路由通过 `Depends(get_ai_client)` 拿到，测试时换成假的）：

```python
import os
import anthropic


class AIUnavailable(Exception):
    pass


MEAL_TOOL = {
    "name": "record_meal",
    "description": "记录用户描述的一餐里的每样食物和估计重量（克）",
    "input_schema": {
        "type": "object",
        "properties": {"items": {"type": "array", "items": {
            "type": "object",
            "properties": {"name": {"type": "string"}, "grams": {"type": "number"}},
            "required": ["name", "grams"]}}},
        "required": ["items"],
    },
}


class AIClient:
    def __init__(self):
        if not os.getenv("ANTHROPIC_API_KEY"):
            raise AIUnavailable("未配置 ANTHROPIC_API_KEY")
        self.client = anthropic.Anthropic()          # 自动读取环境变量

    def parse_meal(self, text: str) -> list[dict]:
        try:
            msg = self.client.messages.create(
                model=os.getenv("AI_PARSE_MODEL", "claude-haiku-4-5-20251001"),
                max_tokens=500,
                system="把用户描述的一餐拆成食物和克数。份量不明确时按常见份量估算："
                       "一碗米饭≈150克，一个鸡蛋≈50克。只调用工具，不要输出其它文字。",
                tools=[MEAL_TOOL],
                tool_choice={"type": "tool", "name": "record_meal"},
                messages=[{"role": "user", "content": text}],
                timeout=15,
            )
        except anthropic.APIError as e:
            raise AIUnavailable(str(e))
        for block in msg.content:
            if block.type == "tool_use":
                return block.input["items"]
        raise AIUnavailable("模型没有返回结构化结果")
```

3. 用 Pydantic 再校验 AI 的输出（这一步是「更准」的关键）：

```python
class ParsedItem(BaseModel):
    name: str = Field(min_length=1, max_length=30)
    grams: float = Field(gt=0, le=2000)

class ParsedMeal(BaseModel):
    items: list[ParsedItem] = Field(min_length=1, max_length=15)
```

4. `POST /ai/parse-meal`（请求体 `{"text": "..."}`，文字 ≤ 500 字）：调 `parse_meal` → Pydantic 校验 → 把结果直接交给 PR-10 的计算函数 → 返回和 `/calories/calculate` 一样的结构，并标注 `from_ai: true`。
5. 功能 B：计算器遇到 `unmatched` 的食物时（有歧义 `ambiguous` 的行仍然让用户自己选，不交给 AI），网页显示「用 AI 估算」按钮；服务端向模型要 `kcal_per_100g`，校验在 0–900 之间才写入 `food_items`，并把 `source` 设为 `ai`，网页上这类行显示「AI 估算」标签。
6. 前端：计算器页面加一个文本框「用一句话描述这一餐」和「AI 识别」按钮。**识别结果只是填进表格里，由用户确认或修改后再点「计算」**（人来把关）。
7. 功能 C（可选）：`POST /ai/report-summary` 把 `GET /report` 的 `summary` 传给模型，提示词里写明「只能引用给定的数字，不要编造、不要给诊断和药物建议」，输出后拼上免责声明。

**做成的效果**：在计算器里输入「一碗米饭加两个水煮蛋」，点 AI 识别，表格自动填出「米饭 150 g、鸡蛋 100 g」，确认后得到 350 kcal。

**如何验证“更准”**（AI 不能靠感觉评估，要有一组题来测）

- 建 `evals/meal_cases.json`，写 10 句话和你**手算**的总热量。例：「一碗米饭加两个水煮蛋」→ 150 g 米饭（195）+ 100 g 鸡蛋（155）= 350 kcal，允许误差 ±20%（280–420）。
- 写 `scripts/eval_meals.py`：对每句话调用 AI 接口，比较总热量是否在允许误差内，打印通过率。跑 3 遍，看结果稳不稳定。
- 对同一句话分别用「纯 AI 直接算总热量」和「AI 拆解 + Python 计算」，比较哪个更接近手算值、哪个跨多次运行更稳定。这就是结论「数字交给 Python」的依据。

**风险与对策**

| 风险 | 会怎么表现 | 对策 |
| --- | --- | --- |
| CORS 报错卡住 | 网页按钮点了没反应，Console 有 CORS 红字 | 确认网页地址的协议、域名、端口都在 `allow_origins` 里；`localhost` 和 `127.0.0.1` 是不同源 |

| 日期和时区 | 晚上打卡被当成「未来」 | 服务端用的是自己机器的 `date.today()`，本地开发即用户时区；上线后要改为前端传日期并按用户时区校验 |
| 浮点数边界 | 刚好 110% 被判成超额 | 比较前 `round(ratio, 4)`；体重差也先 `round(diff, 4)`；每个边界都有测试 |
| 两步操作只成功一步 | user 建成了但没有 profile | 注册时做补偿删除（PR-07）；删除时顺序先 profile 后 user |
